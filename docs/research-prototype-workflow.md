# Research Prototype Workflow

Операционный workflow для сборки интерактивного research prototype AltaIDE из Figma и проверенных компонентов Design System.

Главная цепочка:

**Figma → Component Inventory → Ready Components → Screens → Scenario Logic → QA → Research Ready → User Test**

## 1. Hypothesis

**Цель:** понять, что именно проверяет исследование.

Зафиксировать одну конкретную UX-гипотезу. Формулировка должна позволять понять, какой результат подтвердит или опровергнет предположение.

## 2. User task

**Цель:** определить действие, которое должен выполнить респондент.

Записать пользовательскую задачу простым языком, без технических инструкций и подсказок по реализации.

## 3. Screens

**Цель:** определить минимальный набор экранов для полного сценария.

Перечислить стартовый экран, промежуточные состояния и экран/состояние результата. Не добавлять экраны, которые не нужны для проверки гипотезы.

## 4. Component Inventory

**Цель:** понять, из каких DS-компонентов собирается каждый экран.

Перед версткой каждого экрана составить таблицу:

| Figma element | DS component | Status | Action |
|---|---|---|---|

Правила:

- `Ready` — можно использовать в prototype;
- `Generated` — сначала верифицировать;
- `Verifying` — дождаться завершения проверки;
- отсутствующий компонент — зафиксировать gap.

## 5. Gap analysis

**Цель:** не создавать локальные подмены отсутствующих DS-компонентов.

Если необходимого компонента нет или он не покрывает нужное состояние, создать `docs/gap/<scenario-id>.md`.

Минимальная таблица:

| Screen | Figma element | Missing component | Blocks scenario | Decision |
|---|---|---|---|---|

## 6. Component verification

**Цель:** довести только нужные сценарию компоненты до `Ready`.

Для каждого требуемого `Generated` компонента:

1. проверить структуру;
2. сверить с актуальным Figma-компонентом;
3. проверить semantic tokens;
4. проверить variants / states;
5. проверить Light / Dark;
6. проверить interaction и edge cases;
7. проверить keyboard / focus;
8. проверить accessibility;
9. проверить `file://` и GitHub Pages;
10. зафиксировать verification в `docs/component-registry.md`.

Не верифицировать весь backlog заранее.

## 7. Screen composition

**Цель:** собрать экран из уже разрешённых DS-компонентов.

Prototype CSS отвечает только за layout, positioning, grid/flex, размеры зон и screen-specific composition.

Запрещено:

- копировать component CSS;
- менять визуальный слой reusable-компонента;
- создавать локальные версии компонентов;
- использовать prototype как место для исправления Design System.

## 8. State

**Цель:** определить, где живёт изменяемое состояние сценария.

Перед написанием логики ответить:

- где хранится state;
- кто его читает;
- кто его меняет;
- какой UI зависит от изменения.

Для research prototype достаточно локального Vanilla JS state, если задача не требует более сложной модели.

## 9. Interaction

**Цель:** сделать пользовательский flow проходимым, а не только визуально похожим.

Проверить:

- click;
- input;
- select;
- keyboard;
- validation;
- back / cancel;
- retry;
- repeated actions;
- релевантные async-like состояния, если они есть в сценарии.

## 10. Visual QA

**Цель:** подтвердить соответствие экранов Figma.

Проверить композицию, размеры, spacing, typography, цвета, состояния, Light/Dark там, где тема действительно нужна сценарию, и отсутствие prototype-specific визуальных подмен компонентов.

После успешной визуальной проверки статус прототипа может перейти в `Visual QA` или далее, если остальные проверки тоже завершены.

## 11. Interaction QA

**Цель:** убедиться, что сценарий работает не только на happy path.

Пройти flow от начала до результата и проверить:

- все критичные действия;
- неправильный ввод;
- отсутствие данных;
- повторные действия;
- disabled / invalid / loading / error / success состояния, если они релевантны;
- keyboard navigation;
- отсутствие блокирующих console errors.

## 12. Research cleanup

**Цель:** убрать всё, что выдаёт технический прототип вместо пользовательского интерфейса.

В research prototype не должно быть:

- developer/debug UI;
- Figma node IDs;
- имён файлов;
- states matrix;
- технических пояснений;
- сообщений о недостающих компонентах;
- theme switch, если переключение темы не является частью исследования.

## 13. Repository verification

**Цель:** автоматически поймать типовые технические нарушения до публикации и ручного QA.

Из корня репозитория запустить:

```bash
python3 scripts/verify_repo.py
```

Перед переходом к публикации verifier должен завершиться без `ERRORS`.

`WARNINGS` нужно просмотреть вручную и решить, блокируют ли они исследовательский сценарий.

Verifier не заменяет Visual QA, Interaction QA или Figma verification и сам по себе не присваивает `Ready` / `Research Ready`.

## 14. Publish

**Цель:** получить воспроизводимую версию сценария для теста.

Перед публикацией:

- зафиксировать prototype commit;
- зафиксировать DS commit;
- проверить URL GitHub Pages;
- убедиться, что сценарий открывается и проходится в опубликованной версии.

## 15. Registry

**Цель:** зарегистрировать конкретную тестируемую версию.

Обновить `docs/prototypes-registry.md`.

Минимально заполнить:

- ID;
- Scenario;
- Hypothesis;
- Prototype commit;
- DS commit;
- URL;
- Status.

`Research Ready` допустим только после прохождения Research Prototype Gate.

## 16. Tag

**Цель:** сохранить точку, которую реально показывали респондентам.

Перед пользовательским тестом создать понятный Git tag для конкретной версии сценария.

После теста не переписывать эту версию: изменения делать следующей версией сценария.

---

## Research Prototype Gate

Перед статусом `Research Ready` проверить:

### G1. Scenario

- есть гипотеза;
- есть user task;
- есть полный end-to-end flow.

**Блокирующий gate.**

### G2. Visual Fidelity

- экраны сверены с Figma;
- нет очевидных визуальных расхождений, влияющих на исследование.

### G3. Components

- используются только разрешённые `Ready` компоненты;
- нет локальных копий и визуальных overrides.

### G4. Interaction

- критичные действия работают;
- проверены ошибки, validation, back/retry и repeated actions, если применимо.

**Блокирующий gate.**

### G5. States

- реализованы релевантные loading / empty / error / disabled / invalid / success состояния.

### G6. Research Cleanliness

- отсутствует developer/debug UI;
- интерфейс выглядит как продукт, а не как техническая демонстрация.

**Блокирующий gate.**

### G7. Reproducibility

- зафиксированы prototype commit и DS commit;
- есть рабочий URL;
- registry обновлён;
- создан tag перед тестом.

---

## Definition of Done: Research Ready

Прототип готов к исследованию, если:

- гипотеза и user task зафиксированы;
- все необходимые screens существуют;
- flow проходится от старта до результата;
- критичные действия работают;
- используются только допустимые DS-компоненты;
- gaps либо устранены, либо явно не блокируют сценарий;
- component visuals не переопределяются в prototype;
- Visual QA пройден;
- релевантные states реализованы;
- keyboard/focus проверены;
- нет блокирующих console errors;
- `python3 scripts/verify_repo.py` завершён без `ERRORS`;
- GitHub Pages версия работает;
- developer/debug UI отсутствует;
- registry содержит prototype commit и DS commit;
- создан tag для тестируемой версии.
